# Laptiva internationalization

## Purpose and scope

Laptiva ships one static application with three product locales:

| Product locale | Public code | Settings label | Intended copy |
| --- | --- | --- | --- |
| `en` | `en` | English | Product default |
| `es-AR` | `es` | Español (Argentina) | Argentine Spanish with voseo |
| `pt-BR` | `pt` | Português (Brasil) | Brazilian Portuguese |

The localized contract covers the core timer experience:

- Home, timer library and timer editor.
- Runner phases, completion, progress and workout history.
- Settings, reminders and generated calendar-event content.
- Coach personalities, phase cues, contextual speech and display messages.
- System-voice discovery for the active language family.
- Runtime document metadata and installable PWA manifests.
- Accessible names, dates, durations, counts and plural forms.

The following boundaries are intentional:

- Laptiva Labs remains English-only while it is experimental. Its entry point may appear in localized Settings because Settings belongs to the core product, but the Labs screens, prompts, model states and generated candidates are not part of the localization contract.
- Static HTML and social-preview metadata default to English. GitHub Pages serves one static HTML document and client-side code applies the selected locale after load. Locale-specific social previews are not a product requirement.
- Multilingual QA is incremental and based on real use across devices. Automated coverage prevents known regressions but does not replace field testing or native-language review.

## Locale resolution

Locale definitions live in `i18n/locales.ts`. On startup, Laptiva resolves the locale in this order:

1. A supported `lang` query parameter.
2. The value stored under `pulse-locale-v1` in local storage.
3. The first supported language in `navigator.languages` or `navigator.language`.
4. English.

Language-family matching is deliberate:

- Any English tag resolves to `en`.
- Any Spanish tag resolves to `es-AR`.
- Any Portuguese tag resolves to `pt-BR`.
- Unsupported languages fall back to English.

Public URLs use short codes:

```text
https://poligarcia.github.io/pulse-interval-timer/?lang=en
https://poligarcia.github.io/pulse-interval-timer/?lang=es
https://poligarcia.github.io/pulse-interval-timer/?lang=pt
```

A valid URL locale wins over an existing saved preference and is then saved on the device. Changing the language in Settings updates both local storage and the current URL while preserving unrelated query parameters and the hash.

## Architecture

### Core locale layer

| File | Responsibility |
| --- | --- |
| `i18n/locales.ts` | Supported locales, public codes, detection, fallback, URL handling and storage. |
| `i18n/LocaleProvider.tsx` | React locale state plus runtime `lang`, metadata and manifest updates. |
| `i18n/messages.ts` | Typed product copy for all supported locales. |
| `i18n/timerNames.ts` | Rendering automatic timer names from semantic timer values. |
| `i18n/index.ts` | Public exports for consumers. |

`AppMessages` is the localization contract. Every locale is a complete implementation of the same type, so a missing section fails TypeScript rather than silently falling back to mixed-language UI.

The root layout is statically rendered in English. After hydration, `LocaleProvider` sets the resolved `html[lang]`, document title, description, Open Graph/Twitter fields and the matching manifest. This runtime update improves the installed and interactive experience; it is not intended to change crawler-only social previews.

### Semantic data and rendered copy

Persisted product data should remain language-neutral whenever possible:

- Automatic timer names are stored canonically with `nameIsCustom: false` and rendered from Work, Rest, rounds and cycles in the active locale.
- User-entered names and legacy names remain exactly as stored.
- Workout-history snapshots use the same automatic-name rule, so history follows the current locale without rewriting data.
- Progress milestones persist semantic IDs; their titles, descriptions and progress labels come from `AppMessages`.
- Reminder schedules persist weekday numbers and local time. Localized labels and iCalendar text are supplied only when rendered or exported.
- Dates and decimal values use `Intl` with the active product locale.

Do not store a translated label when a stable ID or semantic value can be stored instead. This keeps language changes reversible and avoids migrations when copy changes.

### Coach and messages

Coach localization is split by content type:

| File | Responsibility |
| --- | --- |
| `coach/localization.ts` | Personality presentation, phase cues, contextual phrases and voice previews. |
| `coach/display-message-locales.ts` | Motivational and cooldown display-message libraries. |
| `coach/voices.ts` | Voice filtering and selection for the active language family. |

English motivational messages retain their Mentria attribution and licensing data. English cooldown reflections are original Laptiva copy attributed to Laptiva Coach. Spanish and Portuguese messages are original Laptiva copy and intentionally have no author attribution. Non-English IDs are locale-prefixed and all message IDs are globally unique, so recent-message memory can safely contain entries from multiple languages.

Speech synthesis depends on voices installed by the operating system and exposed by the browser. Laptiva requests the correct language family, but voice availability, names, gender inference and quality vary by device. This requires physical-device QA.

### PWA and offline behavior

Each locale has a manifest with the same application identity and scope:

- `public/manifest.webmanifest`
- `public/manifest.es.webmanifest`
- `public/manifest.pt.webmanifest`

Their `start_url` values include the matching public language code. The service worker precaches every localized manifest. Adding or renaming a manifest requires updating `public/sw.js` and bumping its cache version so installed clients receive the new shell.

## Copy conventions

- Keep **timer** as the product term in all three locales. Do not translate it to cronómetro, temporizador or another regional synonym in product navigation.
- Use Argentine voseo in `es-AR`: for example, “Elegí”, “Guardá”, “Reiniciá” and “Preparate”.
- Use Brazilian Portuguese rather than European Portuguese.
- Prefer functions in `AppMessages` when word order, pluralization or interpolation varies by locale.
- Never build user-facing sentences by concatenating separately translated fragments.
- Preserve user-entered timer names verbatim.
- Keep ARIA labels and confirmation dialogs localized alongside visible copy.
- Treat narrow portrait screens and low-height landscape screens as required layouts. Phase names such as “PREPARACIÓN”, “PREPARAÇÃO” and “DESCANSO ENTRE CICLOS” are regression cases.

## Adding a locale

1. Add the locale to `SUPPORTED_LOCALES` and `LOCALE_OPTIONS` in `i18n/locales.ts`.
2. Extend `matchSupportedLocale` and confirm the intended public URL code.
3. Add a complete `AppMessages` implementation in `i18n/messages.ts`.
4. Add coach presentation, cues, contextual phrases and preview copy in `coach/localization.ts`.
5. Add original or appropriately licensed display-message libraries in `coach/display-message-locales.ts`.
6. Review recommended system-voice names where useful. Language-family filtering itself is derived from the locale.
7. Add a localized manifest, keep the shared app `id` and scope, and use a locale-specific `start_url`.
8. Add the manifest to the service-worker shell and bump the cache version.
9. Extend locale, message, timer-name, coach, reminder and manifest tests.
10. Complete the QA checklist below before declaring core-product support.

Do not expand Laptiva Labs automatically when adding a core locale. That scope requires a separate product decision.

## QA checklist

### Resolution and persistence

- Open each `?lang=en`, `?lang=es` and `?lang=pt` link in a clean browser profile.
- Confirm the URL language wins over a different saved language.
- Change the language in Settings, reload and confirm it persists.
- Confirm unsupported browser languages fall back to English.
- Confirm unrelated query parameters and URL hashes survive a language change.

### Core screens

- Review Home, library, editor, Settings, Progress and empty states.
- Create, edit, reorder and delete both automatic-name and custom-name timers.
- Confirm automatic names change language and custom or legacy names do not.
- Complete a workout and review history, milestones, dates, counts and singular/plural forms.
- Export reminders and inspect summary, description, alarm text and recurrence days.

### Runner

- Exercise Prepare, Work, Rest, cycle rest, Cooldown and Complete.
- Test portrait and landscape, including a low-height landscape viewport.
- Confirm long titles remain inside the viewport and completion content never overlaps the progress summary.
- Confirm displayed messages, phase cues and spoken countdowns use the active language.
- Check screen-reader labels for stage and workout progress.

### Device features

- Test compatible system voices on real iOS, Android and desktop devices where available.
- Install from every localized manifest and confirm the app reopens in the expected locale.
- Reload offline after the service worker has cached the current release.
- Confirm a shared language link still wins inside an already-installed PWA when the platform passes its query string through.

### Linguistic review

- Review `es-AR` for consistent voseo and regional vocabulary.
- Review `pt-BR` with a native speaker before treating the copy as final.
- Recheck layouts after any copy edit; a semantically better phrase may be materially longer.

## Automated verification

Run the full validation set after changing locales or copy:

```bash
npm test
npm run lint
npm run build:github
```

Relevant automated coverage lives in:

- `i18n/locales.test.ts`
- `i18n/messages.test.ts`
- `i18n/timerNames.test.ts`
- `i18n/manifests.test.ts`
- `coach/coach.test.ts`
- `coach/display-messages.test.ts`
- `progress/progress.test.ts`
- `reminders/reminders.test.ts`

Automated tests verify locale resolution, link precedence, storage safety, message contracts, automatic names, coach coverage, localized dates, localized calendar content and PWA identity. Visual and speech behavior still require manual QA.
